Urban data management with Autark DB

Load OpenStreetMap, GeoJSON, CSV with WKT and GeoTIFF into a spatial database that runs entirely in the browser, then query it with SQL and spatial joins.

How to use this page

The examples are cells of one notebook. They share state through ctx: the first cell creates the database and stores it as ctx.db, and later cells reuse it. Run them in order, or press Run all above ▶▶ on any cell to run everything up to it. Edits to the code are saved in this browser.

The first cell loads DuckDB (about 35 MB, from the local Autark build), so it takes a moment. The spatial extension may require network access on first use. The OpenStreetMap cell in section 2.1 asks the public Overpass server and, if that is busy or unreachable, falls back to a copy of the same answers recorded in data/osm/, so the OSM examples do not depend on the live Overpass server (add ?overpass=offline to the URL to skip the live server). The SQL, spatial-join and heatmap cells in 3 and 4 use the OSM tables created in 2.1. The pages must be served over http (see Running it); they do not work from a file:// URL.

1Autark DB

Spatial databases store, index and query geographic data in vector and raster formats. They are needed because conventional databases do not efficiently support the spatial relationships and operations that are central to urban analytics. By combining geometry-aware data types with spatial indexes and query languages, they manage geospatial datasets efficiently. Well-known examples are PostgreSQL with PostGIS, SpatiaLite, and DuckDB with its spatial extension.

Autark DB (autk-db) is the spatial database module of the Autark toolkit. It is powered by DuckDB and runs directly in the browser, with no client-server architecture, so it suits rapid prototyping of urban analytics software. It loads CSV, JSON, GeoJSON, GeoTIFF and OpenStreetMap data, for example from NYC Open Data or OpenStreetMap.

1.1 Initializing a database

Take the AutkDb class, create an instance and call await db.init(), which prepares DuckDB and loads the spatial extension. The cell runner imports @urban-toolkit/autk from this repository's workspace through Vite and supplies it as autk to every cell. The database is kept in ctx.db so later cells can reuse it.

1.2 Workspaces

A workspace is an isolated database context for organizing geospatial tables. A table created in one workspace is not visible in another, which helps when handling several cities or independent analysis scenarios without name conflicts. After initialization there is one workspace, named "autk".

Geometries in a workspace use the coordinate reference system EPSG:3395 (World Mercator), so data from different sources ends up in one consistent projected system.

setWorkspace() changes the current workspace, creating it if it does not exist. Giving each city its own workspace is a natural way to organize data.

2Loading data

2.1 OpenStreetMap data

loadOsm() fetches data from the Overpass API or parses a downloaded OSM extract (pbfFileUrl), and stores the extracted layers as named tables. A simple query interface names the area and the layers; since each layer is its own table, it can later be queried, transformed and returned as GeoJSON.

The area is either a bounding box ({bbox: [west, south, east, north]}, used here) or named OSM areas ({geocodeArea: "New York", areas: ["Battery Park City"]}). We use a box because it keeps the download small: the named form first resolves "New York" to the whole state, and then also downloads every coastline inside the state's bounding box, about 10 MB and over a minute of Overpass time, just to cut the water layer for one neighborhood.

2.2 GeoJSON data

loadGeojson() stores a GeoJSON FeatureCollection as a named table; outputTableName names it. The GeoJSON can come as a file URL or as an in-memory object. Afterwards, getLayer() reads a named table of the current workspace back as GeoJSON.

2.3 CSV with WKT data

loadCsv() stores a CSV as a named table. When the file holds geometry as WKT, tell it which column through geometryColumns. Here the column wkt becomes the spatial layer at import time.

2.4 GeoTIFF data

loadGeoTiff() stores a raster as a named table; pass the file contents as an ArrayBuffer. Here elevation.tif becomes the raster table terrain. getRaster() reads it back as a raster FeatureCollection for rendering or analysis.

3Analytical queries

Analytical queries use rawQuery(), which runs SQL directly on the tables of the current workspace. Because DuckDB manages the data in the browser, the familiar patterns of filtering, grouping and aggregation work without leaving the page. They support OLAP-style workflows, in which datasets are summarized across dimensions and measures. The examples query the park layer loaded in 2.1.

3.1 Filtering data

A filter keeps the records that satisfy a condition. This query reads table_osm_parks and keeps parks whose area exceeds a threshold, returning a few descriptive attributes.

rawQuery() has different output modes through output. With RETURN_OBJECT the result comes back as an array of JavaScript objects, handy for inspection, summaries and intermediate results. With CREATE_TABLE the result is stored as a new table in the current workspace, named by tableName; optional source and tableType metadata let it be treated as a new dataset for later retrieval or visualization.

3.2 Grouping data

Group-by queries summarize data by category. This one counts park features and sums their areas by category, using attributes already present in table_osm_parks.

4Spatial queries

4.1 Spatial join

spatialQuery() performs a spatial join between two tables already in the current workspace. It takes a root table and a join table and enriches the root table with information derived from the spatial relationship of their geometries. That answers questions such as how many nearby features surround each polygon, or how values from one layer aggregate into another. Here we count nearby park features around each surface geometry.

The root table is updated in place. Retrieve it with getLayer() to inspect the enriched geometries and properties.

4.2 Heatmaps

buildHeatmap() builds a regular grid over the workspace extent and aggregates values from a source table into its cells using a spatial proximity rule. Below, each cell of a 40×40 grid stores the number of park features within 200 m, giving a compact raster that can be retrieved with getRaster() for visualization and analysis.
