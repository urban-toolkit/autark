GPU computing with Autark Compute

Custom analysis that runs on the GPU in your browser and attaches its results to the GeoJSON features it describes.

Autark Compute needs WebGPU. It is on by default in Chrome and Edge 113+; Firefox needs Nightly with WebGPU enabled. Section 3 asks the public Overpass server for OpenStreetMap data and falls back to a bundled copy if it cannot be reached. Cells share state through ctx; run them in order or use Run all above ▶▶.

1Autark Compute

Urban analysis often starts with a question about individual features: How compact is this building footprint? What score should we give this street? How much sky is visible from a location? Autark Compute (autk-compute) runs custom analysis on the GPU, directly in the browser, and attaches the results to GeoJSON features.

This page introduces two workflows: deriving attributes with ComputeGpgpu (the gpgpuPipeline() workflow) and estimating visibility with ComputeRender (renderPipeline()). We start with a small, inspectable dataset. The example is designed for learning; at this scale GPU overhead can outweigh its benefits.

1.1 Feature-centric model and GeoJSON data

A GeoJSON Feature combines a geometry with a properties object, and a FeatureCollection groups features. Autark keeps analysis results attached to the feature they describe: a compactness value belongs to a building, and a visibility result belongs to the feature used as a viewpoint.

{
  type: "Feature",
  id: "building-a",
  geometry: { /* GeoJSON geometry */ },
  properties: {
    area: 400,
    perimeter: 80,
    compute: { compactness: 0.7854 }
  }
}

The pipelines return a new collection rather than modifying the original. Keep a reference to the returned collection: downstream cells should use that enriched result.

2Property computation

2.1 The pipeline configuration

The cell above multiplies each measured footprint area by its floor count. Because the inputs come from real buildings, the output varies with both footprint size and height. The configuration has four parts: collection selects the input features; variableMapping exposes area and floors to WGSL; wgslBody defines the calculation; and resultField stores the result at properties.compute.floorArea.

2.2 Mapping feature attributes with variableMapping

The mapping keys are WGSL variable names; the values are paths into the input feature. For example {area: "shape_area"} makes the property shape_area available as area inside WGSL. Both "area" and "properties.area" are valid paths.

Mapped scalar values are 32-bit floats. Missing numeric inputs fall back to zero, so validate required attributes before running a calculation:

2.3 Writing WGSL expressions

WGSL is the shader language of WebGPU. The string passed as wgslBody is the body of a function; the pipeline supplies the mapped inputs. Use floating-point literals such as 1.0, and return a value on every branch.

wgslBody: `
  if (perimeter <= 0.0) { return -1.0; }
  return (4.0 * 3.1415927 * area) / (perimeter * perimeter);
`

Here -1.0 is an explicit sentinel for an invalid perimeter. Exclude or label it in a visualization rather than treating it as a real compactness value, and validate area too when working with external data.

2.5 Example: computing building compactness

For a footprint with area A and perimeter P, define compactness as C = 4πA / P². A circle has C = 1, a square has C = π/4 ≈ 0.7854, and an elongated rectangle has a smaller value. The measure describes shape, not size or building quality.

The cell computes compactness for every building in the sample. A value near 1 means a compact footprint; lower values mean elongated footprints or multipart buildings with more boundary per unit area. The collection keeps the original OSM tags and geometry and adds the result at properties.compute.compactness.

3Render analysis

3.1 The render pipeline

Attribute computation asks what we can derive from a feature's stored values. Render analysis asks what can be seen from a location. The engine renders a scene from sampled camera positions, counts visible content, and attaches aggregated results to viewpoint features.

3.2 Defining the scene and viewpoints

A render analysis begins with the scene: a list of FeatureCollection objects the pipeline can draw. Here the scene is the buildings of Battery Park City and the Financial District in New York City (a bounding box around them), and the viewpoints are the roads there. After loading the data with autk-db, getLayer() returns the building and road layers.

The original notebook loaded a prepared OSM extract (lower_mnt.osm.pbf) so it ran without a network. That file is not part of this repository, so this cell asks the Overpass API for the same two areas. If the public server is busy or unreachable, the cell uses the copy of the same answers recorded in data/osm/, so it also works offline (add ?overpass=offline to the URL to skip the live server). loadOsm() also accepts pbfFileUrl if you have an extract.

The buildings become the scene. The pipeline also needs a viewpoints collection, which fixes where each camera goes. Each road feature is sampled at its centerline midpoint, which becomes the camera location, and sampling.directions sets the viewing directions. With one direction the output is a fast first-pass exposure estimate for every road feature.

const layers = [{id: "buildings", collection: pbfBuildings, type: "buildings"}];
const viewpoints = {collection: pbfRoads, sampling: {directions: 1}};

3.3 Aggregating render results

Next, choose how the rendered pixels are aggregated. This choice decides the metric returned for each viewpoint, such as the visible share of a class or the set of visible objects.

This example treats pixels not covered by a scene layer as sky. With class aggregation, that uncovered background contributes to the sky class. By contrast, {type: "objects"} reports the individual visible objects; to match object results back to source data, give each scene layer a stable objectIdProperty.

Camera settings control the field of view and clipping distances. tileSize sets the resolution of each sample and must be a multiple of eight. The camera extent, sampling strategy, scene completeness and resolution all influence the result.

const aggregation = {
  type: "classes",
  includeBackground: true,
  backgroundLayerType: "sky",
};

The sky component is at properties.compute.render.classes.sky. Object aggregation writes to properties.compute.render.objects. Inspect the output before choosing fields for a table or color scale, and during validation keep a missing result distinct from a measured zero.
